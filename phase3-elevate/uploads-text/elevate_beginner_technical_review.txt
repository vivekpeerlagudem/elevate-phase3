## 1. The AI Insight Pipeline, File by File

The AI pipeline is the single most important thing to understand in this
service. In plain English, this is what it does:

> When a Teams meeting ends and Microsoft produces a transcript, Elevate
pulls that transcript, hands it to an LLM seven times with seven
different prompts, and stores the seven answers in seven database tables.

Here is every file involved, in the order the code visits them.

### 1.1 The entry point — `src/handlers/llm/meeting_insights.py` (94
lines)

**What it does:** picks which of the seven insight tasks to run.

**Key function:** `queue_meeting_insights_generation(transcript_id,
insight_type=None)` at line 35.

**Behaviour (CONFIRMED):**

- If `insight_type` is `None` or `"all"` (lines 54, 66), it dispatches
**one orchestrator task** (`process_meeting_insights`) that fans out into
all seven.
- If `insight_type` is one of `summary`, `minutes`, `key_notes`,
`action_items`, `commitments`, `sentiment_analysis`,
`upsell_opportunities`, it dispatches **just that one task** (lines 74-
77).
- Any other value raises `ValueError` with the allowed list (lines 69-
73).

The map between the insight-type string and the Celery task function is
at **lines 24-32**. Memorise this map — it is the whole dispatcher:

```
"summary"              → process_meeting_summary
"minutes"              → process_meeting_minutes
"key_notes"            → process_meeting_key_notes
"action_items"         → process_meeting_action_items
"commitments"          → process_meeting_commitments
"sentiment_analysis"   → process_meeting_sentiment_analysis
"upsell_opportunities" → process_meeting_upsell_opportunities
```

**Beginner's note:** the handler does **not** check that the transcript
exists in the database. That check happens inside the worker (step 1.3).

### 1.2 The orchestrator task —
`src/worker/tasks/llm/process_meeting_insights.py`

**What it does:** a Celery **chord**. A chord is "run these tasks in
parallel, then run this callback when they are all done."
- **Header (chord)** — the task decorator at line 18, name
`llm.process_meeting_insights`. Fans out the seven per-insight tasks.
- **Callback** — the task decorator at line 96, name
`llm.process_meeting_insights_final_callback`. Runs after the seven
succeed; it is where the notification email and the `mark_dirty` calls
happen.

### 1.3 The seven worker tasks —
`src/worker/tasks/llm/process_meeting_<X>.py`

All seven follow an identical pattern. The decorator line is **13** for
six of them and **15** for upsell:

```
@celery_app.task(name="llm.process_meeting_summary")
def process_meeting_summary_task(transcript_id: str, **kwargs):
    logger = get_logger(__name__)
    try:
         result = asyncio.run(process(transcript_id))
         return result
    except Exception:
         logger.exception("...")
         raise
```

**Beginner's note:** the wrapper does **almost nothing**. The real work
lives in `src/worker/utils/llm/process_meeting_<X>.py`.

### 1.4 The real worker util —
`src/worker/utils/llm/process_meeting_summary.py` (198 lines)

Read this file top-to-bottom. It is the canonical example — the other six
workers follow the same template.

**Line-by-line walkthrough:**

| Lines | What happens | In plain English |
|---|---|---|
| 50-62 | Open a DB session; load the transcript row by UUID | "Find the
transcript in the database. If it is not there, bail out." |
| 64-76 | Load the meeting row via `transcript.parent_id` | "Find the
meeting the transcript came from." |
| 90, 169-197 | `_prepare_messages(transcript, meeting)` renders two
Jinja2 templates (`system.md.jinja`, `user.md.jinja`) | "Fill out a
system prompt and a user prompt with meeting details and transcript
text." |
| 103 | `resp = await run_llm(messages)` | "Call the LLM and wait for the
answer." |
| 105 | `summary_content = resp["choices"][0]["message"]["content"]` |
"Pull the plain-text answer out of the response envelope." |
| 118-126 | `upsert_meeting_insight(...)` writes to `meeting_insights` |
"Save the answer. If a row already exists for `(transcript_id,
'summary')`, replace its content." |
| 144-166 | Two except blocks: `ValueError` and `Exception` | "If
anything went wrong, log it with full detail and re-raise so Celery marks
the task failed." |
**Thing to notice (CONFIRMED gap):** on line 103, `run_llm(messages)` is
called **without** passing `llm_run_payload`. That means no `LlmRun`
tracking row is created for this insight. The infrastructure for tracking
LLM runs exists, but these seven workers do not use it. Ask Mahesh
whether this is intentional or an oversight.

### 1.5 The LLM client — `src/services/llm/litellm.py` (172 lines)

The actual LLM call. This file is small enough to read in one sitting.

**Key function:** `async def run(messages, model=None, temperature=None,
llm_run_payload=None)` at line 64.

**What it does, in order:**

| Lines | What happens |
|---|---|
| 90-92 | Fall back to `cfg.llm_model` and `cfg.llm_temperature` when
caller passes `None` |
| 94-100 | If `llm_run_payload` is provided, insert a row into `llm_runs`
with `status="in_progress"` and the current Celery `task_id` +
`trace_id`. Otherwise `llm_run_id = None`. |
| 114 | Call `completion(**kwargs)` — the actual LLM request |
| 117-131 | Log the token counts (prompt / completion / total) and
`finish_reason` |
| 142 | If a tracking row exists, update it to `status="completed"` |
| 146-171 | On exception: log, update tracking row to `status="failed"`
with `error_details`, re-raise |

**Three things to understand here:**

1. **Temperature is stripped for certain models.** Lines 17-19 define a
`_NO_TEMPERATURE_PREFIXES` tuple of `("gpt-5", "o1", "o3", "o4")`. When
the model string starts with any of these, `temperature` is **not** sent
(lines 51-61). This matters because those model families reject
temperature as an argument.
2. **Token counts are logged but not saved.** The `_update_llm_run`
payload only has `status` and `error_details`. The token numbers end up
in your JSON logs, nowhere else. Building cost dashboards means parsing
logs.
3. **The function is `async def` but the call inside it is synchronous.**
`litellm.completion()` on line 114 is a blocking call. The `async def`
wrapper is cosmetic.

### 1.6 The prompt renderer — `src/utils/prompts.py` (57 lines)

**Key function:** `render_messages(system_path, user_path, **ctx)` at
line 42.

What it returns:

```
[
    {"role": "system", "content": render(system_path)},        # NO ctx
    {"role": "user",   "content": render(user_path, **ctx)},   # ctx
passed in
]
```
**Note (CONFIRMED):** the system prompt is rendered **without** context
variables. Only the user prompt gets `**ctx`. If you put `{{ title }}` in
a `system.md.jinja`, it will crash under `StrictUndefined` (line 15).

**Security note:** `autoescape=False` on line 23. Transcript text is
injected into the user prompt **verbatim**. A hostile transcript could,
in theory, contain instructions aimed at the LLM. This is a known "prompt
injection" surface and worth flagging.

### 1.8 The database write — `src/repositories/llm/meeting_insights.py`

Called from the worker util on line 119. It upserts into the
`meeting_insights` table using the composite unique constraint
`(parent_id, insight_type)` (CONFIRMED — see
`src/models/meeting_insights.py:30`).

### 1.9 Beyond meeting-level insights — cross-entity AI

There is a second AI pipeline for cross-entity insights (customer
sentiment trends and project alerts). It is driven by a **dirty flag**
pattern.

- **When a meeting insight is saved**, the orchestrator callback (step
1.2) calls `mark_dirty("customer_sentiment_trend", customer_id)` and
`mark_dirty("project_alerts", project_id)`. This writes a row into
`ai_insight_jobs`.
- **Every 2 minutes**, Celery Beat runs `process_ai_insights_scheduler`
(`src/worker/utils/llm/process_ai_insights_scheduler.py`, 99 lines). This
claims up to 50 pending jobs with a 180-second debounce (lines 28-32).
- **For each claimed job**, it dispatches `process_ai_insight_generate`.
That task runs with `bind=True, autoretry_for=(), max_retries=0` —
retries are tracked on the job row's `failed_attempts` column, not by
Celery (CONFIRMED
`src/worker/tasks/llm/process_ai_insight_generate.py:18-20`).
- **A reaper** (`process_ai_insight_jobs_reaper`, every 5 minutes) cleans
stuck jobs.
- **A daily coverage sweep** (02:00 UTC) catches anything missed.

## 2. One Teams Transcript, From Webhook to Final Insight

Follow this chapter with your IDE open on the files mentioned. This is
the exact path a transcript takes.

### Step 1 — Microsoft Graph sends a webhook

Microsoft Graph has a subscription on
`users('{uid}')/onlineMeetings/getAllTranscripts`. When a meeting
transcript appears, Microsoft POSTs to our endpoint:

```
POST /api/v1/ms/webhooks/meeting-transcripts/notification
```

**Route:** `src/routes/ms/webhooks/meeting_transcripts.py:17` (function
`meeting_transcripts_notification`).

If the request has a `?validationToken=…` query parameter, we are being
asked to prove ownership of the endpoint — we return the token as
text/plain. Otherwise it is a real notification and we hand it to the
handler.

### Step 2 — The handler deduplicates and queues a worker task

**File:** `src/handlers/ms/webhooks/meeting_transcripts.py`.

For each notification in `payload.value`:

1. **Parse** the `resource` string with a regex to pull out `userId`,
`meetingId`, `transcriptId`.
2. **Deduplicate** with Redis — `SET NX` with a 5-minute TTL on key
`ms_webhook_transcript:{subscriptionId}:{resource}` (line 83). If the key
already exists, this is a duplicate; skip.
3. **Dispatch** a Celery task via
`send_task_with_trace(process_meeting_transcript_notification,
user_id=..., meeting_id=..., transcript_id=...)`.
4. **Return** `{"status": "completed", "total": N, "duplicates": M,
"workers_queued": K}` with HTTP 202 Accepted.

The route finishes in milliseconds. All of the real work happens in the
worker.

### Step 3 — Celery worker picks up the task

**Wrapper:**
`src/worker/tasks/ms/process_meeting_transcript_notification.py:12`.
**Real logic:**
`src/worker/utils/ms/process_meeting_transcript_notification.py::process(
)`.

In order:

1. **Resolve the meeting** — `_fetch_meeting_from_db(meeting_id)` returns
`(parent_id, organizer_user_id)` or `(None, None)`. If missing, return
`{"status":"failed", "reason":"meeting_not_found"}`.
2. **Recording-control guard** — if `config.recording_control_enabled` is
on, read the calendar occurrence and check
`is_disabled_for_capture(occurrence)`. If disabled, return
`{"status":"skipped_user_disabled"}`.
3. **Fetch transcript metadata** — `_fetch_transcript_metadata()` calls
MS Graph `GET /users/{uid}/onlineMeetings/{mid}/transcripts/{tid}`. If
`None`, return `{"status":"failed", "reason":"metadata_fetch_failed"}`.
4. **Fetch transcript content** — `_fetch_transcript_content()` calls MS
Graph `GET .../transcripts/{tid}/content?$format=text/vtt`. If `None`, we
still store the metadata row with `download_status=False` and continue.
5. **Build the row** — `_prepare_transcript_row(parent_id, transcript_id,
metadata, vtt_content)` returns a dict mapping metadata fields onto the
`transcripts` table columns.
6. **Store** — `_store_transcript_in_db()` upserts via
`src/repositories/ms/transcripts.py`. If this fails, return
`{"status":"failed", "reason":"database_storage_failed"}`.
7. **Fan out post-processing** — `_queue_transcript_post_processing()`
builds a Celery **chord**:

```
header   = [ process_meeting_recording_url(parent_id, transcript_id),
             process_meeting_attendance_report(parent_id, transcript_id)
]
callback = process_transcript_post_processing
```

### Step 4 — Post-processing callback runs after both header tasks

**File:**
`src/worker/utils/ms/process_transcript_post_processing.py::process_callb
ack` at line 22.

1. `backfill_meet_now_actuals()` — fill real start/end times if this was
an ad-hoc Meet Now meeting.
2. Queue the recording upload (`process_s3_recording_upload` or
`process_sharepoint_recording_copy` depending on
`config.recording_storage_provider`) with a 30-second countdown so the
recording is likely ready.
3. Queue `process_meeting_insights` with a 60-second countdown — this is
the LLM fan-out from Chapter 1.

### Step 5 — Seven LLM insights run in parallel

Covered in detail in Chapter 1. Each one:

- Loads the transcript and meeting.
- Renders two Jinja2 prompts.
- Calls `litellm.run(messages)`.
- Writes to the appropriate insight table (`meeting_insights`,
`meeting_action_items`, `meeting_commitments`, `meeting_sentiments`,
`meeting_upsell_opportunities`).

### Step 6 — Final callback: notify, stage insight, mark dirty

After all seven succeed, `process_meeting_insights_final_callback`
(`src/worker/tasks/llm/process_meeting_insights.py:96`) does:
- `process_meeting_completed_notification` — sends an email via MS Graph
`POST /users/{sender_id}/sendMail`.
- `process_transcript_stage_insight` — sales-funnel stage detection per
category.
- `mark_dirty("customer_sentiment_trend", customer_id)` and
`mark_dirty("project_alerts", project_id)` — these drop rows into
`ai_insight_jobs`.

### Step 7 — Cross-entity AI insights, 2 minutes later

Celery Beat fires `process_ai_insights_scheduler` every 2 minutes. It
claims the dirty jobs and dispatches `process_ai_insight_generate` for
each. That task:

- Loads customer/project data and all meeting sentiment or ticket data
under it.
- Renders `ai_insight_customer_sentiment_trend/` or
`ai_insight_project_alerts/` prompts.
- Calls LLM.
- Upserts the `ai_insights` table on `(insight_type, reference_id)`.

### What rows exist in the database at the end

After one Teams meeting is fully processed, these rows exist (CONFIRMED
from the FK map):

```
meetings             (1 row, from scheduled calendar sync earlier)
transcripts          (1 row, from Step 3)
meeting_attendance   (1 row, from Step 3 chord header)
s3_storage           (1 row, from Step 4 recording upload)
meeting_insights     (3 rows — summary, minutes, key_notes share this
table
                      via the (parent_id, insight_type) unique constraint)
meeting_action_items (N rows)
meeting_commitments (N rows)
meeting_sentiments (N rows)
meeting_upsell_opportunities (N rows)
transcript_stage_insights (N rows)
ai_insight_jobs     (2 rows — one for customer, one for project;
eventually processed)
ai_insights         (0-2 rows — upserted on (insight_type, reference_id);
may already exist)
llm_runs            (0 rows for meeting insights; see §1.4 CONFIRMED gap)
```

### 3.2 Patterns to notice

**Most endpoints are "trigger a Celery task."** Nearly every POST in the
list above calls `send_task_with_trace(task_fn, …)` inside its handler
and returns HTTP 202. The HTTP response does **not** contain the result
of the work — just a confirmation that it was enqueued. The real work
finishes asynchronously in a Celery worker.

**Webhook endpoints are special.** They do a `validationToken` handshake
for subscription setup, then deduplicate in Redis, then enqueue a Celery
task.
**OAuth endpoints are special.** `GET /oauth/authorize` returns a
`RedirectResponse` to Microsoft's consent page. `GET /oauth/callback`
processes the authorisation code Microsoft sends back. These are the only
two `GET`s with substantial logic.

**One endpoint is `DELETE`.** Only `DELETE /api/v1/transcripts/{id}` uses
the DELETE verb. Deletion of other things (JSM tickets, worklogs) is
handled by soft-delete flows triggered through webhooks.

### 3.3 The ten most important endpoints for a trainee

Learn these first. They cover 80% of what you need to understand to debug
a production incident.

| # | Endpoint | Why it matters |
|---|---|---|
| 1 | `POST /api/v1/ms/webhooks/meeting-transcripts/notification` | The
core transcript webhook. If this is broken, no insights are generated. |
| 2 | `POST /api/v1/llm/meeting-insights` | Triggers the seven-insight
LLM pipeline. The most important LLM endpoint. |
| 3 | `POST /api/v1/meetings/recording` | Stop/start recording. The
feature with the most test coverage (24 test files). |
| 4 | `POST /api/v1/meetings/recording/on-demand` | On-demand Recall AI
bot. Entry point for ad-hoc capture. |
| 5 | `POST /api/v1/jira/webhooks/jsm-tickets/events` | Real-time ticket
sync + sentiment analysis. The Jira counterpart of #1. |
| 6 | `POST /api/v1/recall-ai/webhooks/status` | Recall AI bot status

| 7 | `DELETE /api/v1/transcripts/{transcript_id}` | Cascades to seven

| 8 | `GET /api/v1/aws/recordings/{transcript_id}/access-url` | Pre-

## 4. The 15 Findings in Plain English

Each finding is written for a trainee. For every one you get:

- **What it is** — the plain-English statement
- **Impact** — what could go wrong because of it
- **Evidence** — the file and line proving the finding
- **Uncertainty** — how sure we are
- **Ask Mahesh** — the question to raise

---
### Finding 1 — No authentication inside the service

**What it is:** None of the 64 FastAPI routes check who is calling. There
is no `Depends()` for an auth check anywhere in `src/routes/**`.

**Impact:** If anything can reach the service directly over the network,
it can hit every endpoint. Business endpoints (recording control,
transcript purge, Jira sync triggers) have no built-in gate.

**Evidence:** `grep "Depends(" src/routes/` returns 0 hits. CONFIRMED.

**Uncertainty:** HIGH that there is no in-code auth. UNKNOWN whether a
reverse proxy or API gateway enforces authentication upstream.

**Ask Mahesh:** "Where is API authentication enforced? Is there a reverse
proxy or API gateway in front of this service that I need to configure
for local development?"

---

### Finding 2 — Recall AI webhook signature verification is commented out

**What it is:** Recall AI sends a `webhook-signature` header on every
webhook, and the Svix library can verify it. We have the code but it is

### Finding 6 — Celery routing-key mismatch for 14 short-named tasks

**What it is:** Fourteen tasks are registered with short names like
`llm.process_meeting_summary` using `@celery_app.task(name="llm.…")`. But
the routing map in `src/worker/routing.py` uses the full dotted module
path as the key. Celery matches routes by the registered name, not by
module path.

**Impact:** For scheduled Beat jobs, each entry sets `options={"queue":
"..."}` explicitly, which overrides routing — so Beat is unaffected. For
**ad-hoc dispatches** of these specific tasks from a handler, the message
falls through to `task_default_queue="default"`. If the "default" queue
is not consumed, those tasks never run.

**Evidence:** `src/worker/routing.py:243` for the one correct short-name
entry; the other 13 route keys use dotted paths that will never match.
CONFIRMED.

**Uncertainty:** Whether "default" queue has a consumer. If it does,
nothing visible breaks.

**Ask Mahesh:** "Is the `default` queue consumed by workers in
production? And was the short-name task registration (e.g.
`llm.process_meeting_summary`) intentional?"

### Finding 8 — Token usage is logged but never stored in the database

### Finding 9 — `litellm.completion` is synchronous inside an `async def`

**What it is:** `src/services/llm/litellm.py` imports `from litellm
import completion` (the sync function, not `acompletion`). It is called
at line 114 inside an `async def run(...)`. The function is `async` in
signature only.

**Impact:** The worker calls `asyncio.run(process(transcript_id))`, so
this executes on an event loop that is blocked for the LLM call duration.
Within a single Celery task this is fine (nothing else is running on that
loop). But if any future code expects true concurrency from `await
run_llm(...)`, it will not get it.

**Evidence:** `src/services/llm/litellm.py` imports and line 114.
CONFIRMED.

**Uncertainty:** None.

**Ask Mahesh:** "Was the choice of sync `completion()` over async
`acompletion()` deliberate (e.g. because the worker is single-task-per-
process)? Should new LLM-adjacent code assume concurrency?"

### Finding 10 — `db_session()` docstring is misleading

**What it is:** The docstring in `src/db_engine/db.py:117` says "Commits
automatically on exit." The implementation does **not** commit — it only
closes the session. Repositories own `db.commit()` and `db.rollback()`.

**Impact:** A junior engineer reading the docstring could reasonably
assume the context manager commits for them. If they skip the explicit
commit in a repository, their write is silently lost on session close.

**Evidence:** `src/db_engine/db.py:117` (docstring) vs `:107-131`
(implementation). CONFIRMED.

**Uncertainty:** None.

**Ask Mahesh:** "The `db_session()` docstring says it commits
automatically — the code doesn't. Can we fix the docstring?"

### Finding 11 — No `onupdate=` on any `updated_at` column

**What it is:** Every table has an `updated_at` column with a server
default of `timezone('utc', now())` for inserts. There is no SQLAlchemy
`onupdate=` and no database trigger that bumps the timestamp on `UPDATE`.
The application must set it explicitly on every write.

**Impact:** If a repository forgets to update `updated_at`, the column
keeps the row's original creation timestamp. Audit trails become
unreliable.
**Evidence:** Grep for `onupdate=` across `src/models/` returns 0 hits.
CONFIRMED.

**Uncertainty:** None.

**Ask Mahesh:** "Should we standardise on `onupdate=func.now()` for
`updated_at` across models, or is there a reason this is set in
application code?"

### Finding 12 — No ORM `Relationship()` declarations

**What it is:** All 45 models use SQLModel, but **none** declare a
`Relationship()`. All joins must be hand-coded in repository SQL.

**Impact:** You cannot write `meeting.transcripts` to lazy-load related
rows. Repositories must know the join structure. On the other hand, every
query is explicit — nothing silently emits an N+1 query.

**Evidence:** Grep for `Relationship(` across `src/models/` returns 0
hits. CONFIRMED.

**Uncertainty:** None.

**Ask Mahesh:** "Was the decision to avoid `Relationship()` deliberate
(e.g. to prevent N+1s)?"

### Finding 15 — The seven meeting-insight workers have no Celery retry

**What it is:** All seven
`@celery_app.task(name="llm.process_meeting_*")` decorators are plain —
no `autoretry_for`, no `max_retries`, no `retry_backoff`. If the LLM call
fails (even transiently, e.g. a 429 rate limit), the task fails
terminally for that insight.

**Impact:** A spike of 429s during an LLM provider incident would
permanently lose insights for that batch of meetings. Only the daily
coverage sweep at 02:00 UTC catches gaps.

**Evidence:** `src/worker/tasks/llm/process_meeting_summary.py:13`
through the other six files. CONFIRMED (no retry decorator kwargs).

**Uncertainty:** The daily coverage sweep partially mitigates. The gap is
up to 24 hours.

**Ask Mahesh:** "Should we add `autoretry_for=(litellm.RateLimitError,
litellm.APIError)` with backoff on the meeting-insight tasks?"

## 5. Confirmed Issues vs. Infrastructure vs. Intentional Design

A junior engineer should be able to tell these three categories apart.
Here they are, applied to the 15 findings above.

### 5.1 Confirmed code issues (in-tree problems)

These are things that are clearly imperfect in the code and could be
fixed inside this repository.

| # | Finding | Fix would live in |
|---|---|---|
| 2 | Recall webhook signature verification commented out |
`src/handlers/recall_ai/webhooks/status.py` |
| 6 | Routing-key mismatch for short-named tasks |
`src/worker/routing.py` or task `name=` kwargs |
| 7 | LlmRun not created for insight workers | Each
`src/worker/utils/llm/process_meeting_*.py` |
| 8 | Token usage not persisted on `llm_runs` |
`src/services/llm/litellm.py` + a migration |
| 9 | Sync `completion` inside `async def` |
`src/services/llm/litellm.py` |
| 10 | `db_session()` docstring misleading | `src/db_engine/db.py`
(docstring) |
| 11 | Missing `onupdate=` on `updated_at` | Models + migration |
| 14 | Hardcoded CORS origins | `src/main.py` + config |
| 15 | No retry on meeting-insight tasks | Each insight task decorator |

### 5.2 Possible infrastructure-dependent issues (verify outside the
repo)

These may be fully mitigated by infrastructure we can't see from the code
alone.

| # | Finding | What to verify in infrastructure |
|---|---|---|
| 1 | No in-service authentication | Is there a reverse proxy / API
gateway enforcing auth? |
| 3 | Jira webhook has no signature check | Is Jira sending through a
trusted network path? |
| 4 | MS Graph `clientState` not validated | Does the subscription URL
contain a secret that the proxy enforces? |
| 13 | PostgreSQL not in compose | Is there a shared dev DB, or a
separate compose stack? |

### 5.3 Intentional design choices (not bugs)

| # | Finding | Why it is probably intentional |
|---|---|---|
| 5 | `autoescape=False` on prompt rendering | Prompts are plain text,
not HTML. Escaping would corrupt the content. The trade-off is prompt-
injection surface. |
| 12 | No `Relationship()` declarations | Avoids N+1s by forcing explicit
joins. Cost: no lazy-load navigation. |
| — | One Celery queue per task | Full isolation — a slow task type
cannot block any other. |
| — | `task_acks_late=True` + `worker_prefetch_multiplier=1` | Prefer re-
processing over losing work when a worker crashes. |
| — | All business logic in Celery, not in the request handler | API
returns 202 fast; worker does the heavy lifting with retries available. |
| — | Repositories own commit/rollback | Transaction boundaries live
close to the data layer; handlers can combine multiple reads safely
without being responsible for commits. |

### 5.4 Reading the three categories together

A good mental model when something looks "wrong":

1. First ask: **is this an in-tree code issue?** If yes, write a ticket.
2. Then ask: **might infrastructure already compensate?** If maybe, ask
Mahesh before writing a ticket.
3. Only then ask: **is this an intentional design choice I need to
adopt?** Those usually have a comment or a convention that teaches you
the pattern — read neighbouring files to confirm.
