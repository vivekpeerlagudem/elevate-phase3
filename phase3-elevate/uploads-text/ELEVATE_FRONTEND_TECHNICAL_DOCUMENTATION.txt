 1. Executive Overview
 Elevate 2.0 is a single-page web application (SPA) built with React, TypeScript, and Vite that serves as an internal
 leadership / operations dashboard for Kensium. The application provides authenticated access to five core data
 domains: Employees (users), Projects, Customers, Meetings, and a role-based permissions system (Roles, Modules,
 RolePermissions). The frontend is purely a thin presentation and workflow layer; all data lives in two separate
 ASP.NET-style backend services whose base URLs are configured through environment variables
 (VITE_API_BASE_URL and VITE_Login_API_BASE_URL).

 The code reviewed in this document resides under kensium-solutions-kensium_elevate-2.0-225096fcc9b3/. The src/
 tree contains a flat pages/ folder (16 route components), a small set of layout and UI components, two Zustand
 stores, two hooks, a config/ folder for MSAL (Microsoft 365) wiring, and a single API service module src/api/api.ts that
 centralises all REST calls.

 Microsoft 365 (Azure AD / MSAL) single sign-on is implemented in the codebase but is currently disabled. The MSAL
 provider in src/main.tsx and the O365 button in src/pages/Login.tsx are commented out with explicit // TODO:
 Uncomment for production to enable Microsoft 365 login markers. The active sign-in path is username/password
 against the backend /api/User/login-with-password endpoint.

 The Dashboard page is a static placeholder (hard-coded 0 values); charts and real KPIs are not wired. The majority
 of implemented functionality consists of CRUD list / edit screens for the five domains and the role-permission matrix
 editor.

 7. State Management and Data Flow
 Global state is intentionally minimal. The project uses Zustand for a single meaningful store (useAuthStore) plus a
 near-empty counter store (useStore) that is not used by any production page.

 7.1 useAuthStore — src/store/useAuthStore.ts
 Shape (AuthState):
  user: User | null                        // { id, username, email, name, ... }
  isAuthenticated: boolean
  loading: boolean
  error: string | null
  loginMethod: 'credentials' | 'o365' | null
  login(username, password): Promise<void>
  loginWithO365(account, accessToken?): Promise<void>
  logout(): void
  clearError(): void

 The store is wrapped in Zustand's persist middleware with name 'auth-storage' and a partialize that persists only
 user, isAuthenticated, and loginMethod into localStorage. Loading, error, and the full O365 access token are not
 persisted.

 login() calls loginApi.verifyUserCredentials(), which POSTs to {apiBaseUrl}/api/User/login-with-password with {
 email, passwordHash }. On success, it writes the response body into user, sets isAuthenticated=true, and tags
 loginMethod='credentials'. On failure it stores the error message and re-throws.

 loginWithO365() is invoked after an MSAL popup resolves. It calls loginApi.checkUserByEmail(email) against
 {apiBaseUrl}/api/User/login; if the user exists the MSAL account plus any DB fields are merged into user and
 loginMethod='o365' is set.

 7.2 Local component state
 Each page manages its own data with useState + useEffect: records, loading flag, error string, pagination page,
 column filters, and search text. There is no shared cache and no request de-duplication; every mount of
 EmployeeList re-fetches the full user list.

 7.3 Data flow pattern
  User action (click / submit)

 8. API Integration and Endpoint Inventory
 All HTTP calls originate from src/api/api.ts. Two base URLs are configured:
  VITE_API_BASE_URL       default: https://localhost:5001/
  VITE_Login_API_BASE_URL default: https://localhost:7115/                     // currently exported but all auth
                                                                               // calls below actually use apiBaseUrl

 The ApiClient class is a thin wrapper around fetch:

     • Normalises Content-Type: application/json.

     • Joins baseURL + endpoint with a single '/'.

     • Parses ASP.NET Core ModelState-style errors objects into semicolon-joined messages, and preserves
     errorData.title / message fallbacks.

     • Attaches the parsed body as error.response = {status, data} for callers that want it.

     • Does not attach any Authorization header — no bearer token is sent on data requests.

 10. Authentication and Authorization
 10.1 Credentials-based sign-in (active)
 Covered in §9.1. Credentials are posted directly to the backend; no Authorization header is attached to subsequent
 data requests. There is no token refresh mechanism and no evidence of a cookie-based session either. In short, the
 frontend treats isAuthenticated in Zustand as the sole authority — anything that re-hydrates it (persisted localStorage)
 will grant client-side access to protected routes, regardless of backend session state. Any real authorization must
 be enforced on the backend.

 10.2 O365 single sign-on (dormant)
 MSAL is configured in src/config/msalConfig.ts:
  clientId    ← VITE_AZURE_CLIENT_ID
  tenantId    ← VITE_AZURE_TENANT_ID
  authority   ← VITE_AZURE_AUTHORITY (fallback https://login.microsoftonline.com/<tenant>                   or /common)
  redirectUri ← VITE_AZURE_REDIRECT_URI (fallback window.location.origin)
  cache.cacheLocation = 'sessionStorage'
  scopes      = ['User.Read']

 The provider wrap and all O365 UI are commented out but intact (see §4.2 and §9.2). Enabling it requires
 uncommenting the MsalProvider block in src/main.tsx, uncommenting the button and the handleO365Login handler in
 src/pages/Login.tsx, and providing the three VITE_AZURE_* environment values.

 10.3 Route protection
 ProtectedRoute.tsx is a simple Outlet gate. Every non-login route in App.tsx is wrapped by it. There is no role-based
 route restriction on the frontend — any authenticated user can navigate to every page, including role management
 and permission editing. The RolePermissions feature is the mechanism by which the backend is expected to enforce



Elevate 2.0 — Frontend Technical Documentation                                                                     Page 11
 finer authorization.

 10.4 Logout
 Sidebar.handleLogout (Sidebar.tsx:43) performs: optional MSAL logoutPopup → useAuthStore.logout() →
 navigate('/login'). The logout() action clears user/isAuthenticated/loginMethod/error, which Zustand's persist
 middleware then flushes to localStorage.


 11. Forms, Validation, and User Interactions
 No form library is used. All forms are built with native inputs, controlled by local useState, and submitted through
 onSubmit/onClick handlers. Validation is HTML-level only (required, type="number", type="email") plus imperative if
 checks in save handlers. There is no schema validation (zod / yup) and no field-level error UI framework; errors are
 shown as inline banners pulled from backend responses.

 Notable forms: Login.tsx, EmployeeEdit.tsx, ProjectEdit.tsx, CustomerEdit.tsx, Roles.tsx, RolePermissions.tsx. Rich
 text fields use the custom editor described in §6.1.

 User interactions: client-side search + column filters + pagination (20 rows) are implemented repeatedly in each list
 page (duplication rather than a shared table component). CSV export is implemented inline in EmployeeList; other list
 pages do not export.


 12. Styling and UI Architecture
 Tailwind CSS 3.4 drives all styling. tailwind.config.js scans ./src/**/*.{ts,tsx} (plus pages / components / app roots,
 which are unused). The config declares a darkMode: ['class'] strategy and extends the theme with
 CSS-variable-backed semantic tokens: background, foreground, primary, secondary, destructive, muted, accent,
 popover, card, each with a -foreground pair. The variables themselves are defined in src/index.css.

 Dark mode: the Tailwind strategy is class-based, but no component toggles the .dark class on <html>; dark mode is
 latent, not active.

 UI primitives: components/ui/Button.tsx uses class-variance-authority for variants and components/ui/Card.tsx
 provides a shadcn-style card. The sidebar uses a hard-coded brand color #092540 and the login button uses
 #4D9078, outside the CSS-variable system.

 Icons: lucide-react is used consistently (Menu, Users, Briefcase, LayoutDashboard, ShieldCheck, Calendar,
 AlertCircle, …).

 Helper: src/lib/utils.ts exports cn(...inputs) = twMerge(clsx(inputs)), used across most components to compose
 conditional class strings.


 13. Error Handling and Asynchronous Processing
 13.1 Transport-level
 The ApiClient.request method parses non-2xx responses, specifically handling ASP.NET Core's ModelState shape ({
 errors: { field: string[] } }) and the ProblemDetails shape (title / message). It then throws a normal Error enriched with
 .response = { status, data }.

 13.2 Component-level
 Every page keeps a local error string that renders as a red inline block. There is no toast system and no global
 error boundary. Loading states are inline text (Loading employees…, Logging in…) or a disabled button; there is no
 spinner component.

 13.3 Async orchestration



Elevate 2.0 — Frontend Technical Documentation                                                                       Page 12
 Fetches use async/await inside useEffect. Several pages do not include cleanup/cancellation (AbortController is not
 used), which means a rapid navigation can cause a setState on an unmounted component (silent memory leak
 warning in React 18 is suppressed but the race remains).

 The useApi hook (hooks/useApi.ts) offers a generic { data, loading, error, execute } wrapper, but inspection of pages
 shows it is seldom wired in; most pages roll their own.


 14. External Integrations
 14.1 Microsoft Entra ID / Microsoft 365 (@azure/msal-browser, msal-react)
 Full-featured popup OAuth flow with scope User.Read. Access tokens from MSAL are stored in sessionStorage; after
 a successful popup the frontend forwards only the account.username (email) to the backend /api/User/login endpoint
 to verify the user exists. The MS Graph endpoint (https://graph.microsoft.com/v1.0/me) is referenced in msalConfig.ts
 but is not called anywhere in src/.

 14.2 Backend REST services
 Two base URLs are configured but all live calls currently target VITE_API_BASE_URL. The
 VITE_Login_API_BASE_URL value is exported from src/api/api.ts but is unused at the moment — loginApi methods
 explicitly use config.apiBaseUrl / API_BASE_URL.

 14.3 Jira / Tempo (indirect)
 Field names such as issueId, issueKey, parentIssueKey, and tempoAccountName on Project and Customer
 interfaces indicate the backend is populated from Atlassian Jira and Tempo. The frontend does not call Jira or Tempo
 directly; it only consumes the hydrated records from the backend.

 14.4 SharePoint
 Customer.sharePointUrl is a plain external link rendered in the UI; no SharePoint SDK is used.

 16. Important Dependencies and Limitations
 16.1 Dependencies worth highlighting
     • @azure/msal-browser / msal-react — carried as a dependency even though the active build does not
     instantiate the provider. The bundle will still include MSAL in production.

     • axios — declared but unused. Safe to remove.

     • zustand — only two stores exist (useAuthStore, useStore); the latter is unused by production pages.

     • tailwindcss-animate — only used via Tailwind config; no custom animations defined in the app.

 16.2 Limitations / smells observed in code
     • Dashboard is static placeholder content — no real metrics.

     • No central Authorization header; the frontend never sends a bearer token. Session trust is purely client-side
     (isAuthenticated in Zustand persisted to localStorage).

     • Password is sent in plaintext in the passwordHash field; name is misleading. The real hashing must happen
     server-side.

     • Each list page re-implements search, filter, sort, pagination from scratch — large duplication.

     • No request cancellation on route change (no AbortController).

     • No error boundary; a runtime error in a page unmounts the whole subtree with no fallback UI.

     • No tests of any kind (no __tests__, no *.test.ts, no test runner in package.json).

     • Home.tsx and About.tsx are orphaned.

     • Full-object PUT on Projects and Customers risks lost-update bugs on concurrent edits.

     • exampleApi in src/api/api.ts (/users) is scaffolding and unused.

     • Access-Control-Allow-Origin: * in web.config is permissive; harmless for a static site but worth reviewing.

 17. Unverified Behavior and Questions Requiring
 Backend Investigation

Elevate 2.0 — Frontend Technical Documentation                                                                       Page 14
 The following statements rely on backend behaviour that cannot be confirmed from the frontend alone. A new
 engineer should verify these against the backend repository before relying on them.

     • Does POST /api/User/login-with-password return a bearer token, cookie, or neither? The frontend stores
     whatever JSON comes back as user and never looks for an access_token field. If the backend does set an
     HttpOnly cookie, cross-origin deployments must enable credentials: 'include' — the current fetch wrapper does
     not.

     • How does the backend treat the plaintext passwordHash field? Is it actually a hash (client-side hashing not
     visible in the code), or raw password?

     • How does the backend recognise an O365-authenticated caller? The frontend forwards only { email }; no MSAL
     id_token / access_token is sent to /api/User/login.

     • What is the exact PermissionType enum on the server? Frontend sends snake_case strings (no_access,
     view_basic, view_all, full_access) but a comment in RolePermissions.tsx says the API expects PascalCase. One
     of the two is wrong.

     • Does GET /api/User/{id} accept lowercase GUIDs? The frontend uppercases them before sending; verify the
     backend doesn't care, or that this isn't working around a case-sensitive route.

     • Does PUT /api/Project/{id} accept the full Project body including server-managed fields (createdAt, loggedHours,
     …)? Full-object PUT is unusual.

     • What rules define a project / customer as Needs Attention? The predicates live in the frontend; is that the
     intended source of truth, or should the backend expose a dedicated endpoint?

     • Is VITE_Login_API_BASE_URL (default https://localhost:7115/) a dead configuration, or a planned split that the
     frontend has not yet migrated to?

     • Does /api/RolePermission/bulk delete-and-replace, or append? The frontend's edit flow explicitly DELETEs each
     existing permission first; if the bulk endpoint is already a replace, the deletions are redundant.

     • Is there a backend-driven menu / permission check that should hide items the user cannot access? The sidebar
     menu is hard-coded.
