## 1. Executive Summary

**Kensium Elevate AI** is a FastAPI + Celery backend service that:

1. **Captures Microsoft Teams meetings** — subscribes to MS Graph
webhooks for transcript events, downloads VTT transcripts, and stores
recordings in AWS S3 (or SharePoint legacy).
2. **Captures external-platform meetings** — for meetings organized
outside the MS tenant, deploys Recall AI recording bots to join Zoom,
Google Meet, and other platforms.
3. **Generates LLM-powered insights** — runs each transcript through 7
analysis types (summary, minutes, key notes, action items, commitments,
sentiment, upsell opportunities) plus cross-entity AI insights (customer
sentiment trends, project alerts).
4. **Syncs Jira/JSM data** — periodically fetches accounts, customers,
projects, licenses, and tickets from Jira Service Management; performs
real-time webhook-driven ticket sync with LLM sentiment analysis.
5. **Syncs Tempo work logs** — incremental 15-minute sync from the Tempo
API.
6. **Provides recording control** — users can stop/start recording per
occurrence or series, with Do Not Record domain enforcement.
7. **Serves a REST API** — 26 routers under `/api/v1`, consumed by the
Elevate web frontend (separate repo).

**Technology Stack (CONFIRMED):**
- Python 3.13+ / FastAPI / Uvicorn
- Celery 5 + Redis 7.4 (broker) + PostgreSQL (result backend)
- SQLModel/SQLAlchemy ORM + Alembic migrations
- LiteLLM (LLM abstraction — actual provider UNKNOWN from code)
- httpx (async HTTP client)
- boto3 (AWS S3)
- Jinja2 (LLM prompt + email templates)
- Docker Compose (5 services) + OpenTelemetry → SigNoz
- Poetry (dependency management)

**Scale indicators:** ~70+ Celery tasks, ~80 dedicated queues, 38+ ORM
models, ~70 Alembic migrations, 180 test files, 11 LLM prompt template
sets.

### 3.2 Layered Architecture (CONFIRMED from source)

The application follows a strict layered architecture:

1. **Routes** (`src/routes/`) — FastAPI router definitions. Thin
controllers that parse HTTP input, call handlers, return responses. No
business logic.
2. **Handlers** (`src/handlers/`) — Business logic orchestration. Load
data from repositories, validate, apply rules, enqueue Celery tasks.
Handlers own the decision of what to do.
3. **Repositories** (`src/repositories/`) — Database access layer. Pure
CRUD operations on specific models. Own commit/rollback.
4. **Services** (`src/services/`) — External API clients. Make HTTP calls
to MS Graph, Jira, Recall AI, Tempo, AWS S3, LLM. No database access.
5. **Worker Tasks** (`src/worker/tasks/`) — Thin Celery task wrappers.
Each task function delegates immediately to a corresponding
`worker/utils/` function.
6. **Worker Utils** (`src/worker/utils/`) — Business logic for background
processing. The real implementation behind each task. Call services +
repositories.
7. **Models** (`src/models/`) — SQLModel/SQLAlchemy ORM definitions.
Define table schema.
8. **Schemas** (`src/schemas/`) — Pydantic models for request/response
validation and serialization.

## 6. FastAPI and Backend Fundamentals

### 6.1 Application Creation (CONFIRMED: `src/main.py`)

```python
app = FastAPI(title="Elevate AI Service")
```

No lifespan hooks, no startup/shutdown events, no custom exception
handlers are registered at the app level. The application relies on
Alembic (run in the entrypoint script) for database initialization.

### 6.2 Router Registration (CONFIRMED: `src/main.py:59-87`)

A single `APIRouter(prefix="/api/v1")` is created, all 26 domain routers
are included into it, then it is included into the app. No authentication
dependencies are applied at the router level.

### 6.3 Middleware Stack (CONFIRMED: `src/main.py:54-57`)

Order (outermost first):
1. **LoggingMiddleware** — `BaseHTTPMiddleware` subclass. Injects
`trace_id` (from `X-Trace-ID` header or UUID) and `request_id` (UUID)
into context vars. Logs request start/end. Adds `X-Trace-ID` and `X-
Request-ID` to response headers. Skips `/health`.
2. **CORSMiddleware** — Allows origins: `http://183.82.120.94:4173` and
`https://elevate.kensium.com`. All methods, all headers.

```python

    1. Create LlmRun record in DB (status="pending")
    2. Call litellm.acompletion(model=config.llm_model,

## 11. End-to-End Business Workflows

### 11.1 Workflow: Scheduled Meeting → Insights

```
Trigger: Celery Beat daily 00:45 UTC
  ↓
1. process_calendar_events_sync
   → For each user: GET calendar events from MS Graph
   → Store/update in calendars table
   → For each external meeting: queue process_ms_meeting
  ↓
2. process_ms_meeting
   → GET online meeting details from MS Graph
   → Create/update meetings row
   → Queue process_meeting_transcript_subscription_create
  ↓
3. process_meeting_transcript_subscription_create
   → POST subscription to MS Graph for transcript events
   → Store subscription in ms_subscriptions table
  ↓
4. [Meeting occurs, transcript is generated by Teams]
   → MS Graph sends webhook to /api/v1/ms/webhooks/meeting-transcripts
  ↓
5. Webhook handler deduplicates, queues
process_meeting_transcript_notification
  ↓
6. process_meeting_transcript_notification
   → Fetch transcript metadata + VTT content from MS Graph
   → Check recording control overrides
   → Check Do Not Record domains
   → Store transcript row
   → Build Celery chord: [recording_url, attendance] → post_processing
  ↓
7. process_transcript_post_processing
   → Backfill Meet Now actuals
   → Queue S3 recording upload (30s delay)
   → Queue process_meeting_insights (60s delay)
  ↓
8. process_meeting_insights → dispatches 7 tasks:
   → process_meeting_summary
   → process_meeting_minutes
   → process_meeting_key_notes
   → process_meeting_action_items
   → process_meeting_commitments
   → process_meeting_sentiment_analysis
   → process_meeting_upsell_opportunities
   Each: load transcript → render prompt → LLM call → parse → store
  ↓
9. Post-insight:
   → process_meeting_completed_notification (email)
   → process_transcript_stage_insight (sales stage)
   → mark_dirty → triggers AI insight regeneration
  ↓
10. AI insights scheduler picks up dirty jobs
    → process_ai_insight_customer_sentiment_trend
    → process_ai_insight_project_alerts
```

### 11.2 Workflow: External Meeting → Recall AI Capture

```
Trigger: Calendar sync detects external meeting (organizer outside
tenant)
  ↓
1. process_bot_create
   → POST to Recall AI API: create bot with join URL
   → Store bot row in recall_ai_bots table
  ↓
2. [Bot joins meeting, records it]
   → Recall sends webhook (recording.done) to /api/v1/recall-
ai/webhooks/status
  ↓
3. process_recall_webhook
   → Routes based on event type
   → For recording.done: fetch transcript + participants from Recall API
   → Store transcript (with transcript_raw_json for Recall format)
   → Queue process_recall_transcript_post_processing
  ↓
4. Same LLM insight pipeline as MS meetings (step 8+ above)
```

### 11.3 Workflow: On-Demand Recording

```
Trigger: User clicks "Record" in Elevate UI for a meeting in progress
  ↓
1. POST /api/v1/on-demand-recording {email, join_url}
  ↓
2. Handler:
   → Acquire Redis lock (per join_url)
   → Validate requester (user exists, active)
   → Classify join URL (Teams, Zoom, etc.)
   → Check: internal organizer? → reject (auto-captured)
   → Check: existing active bot? → reject
   → Check: recording stopped? → reject
   → Check: Do Not Record domain? → reject
   → Synchronously create Recall AI bot
   → Store bot + meeting rows
   → Release lock
   → Return 201
  ↓
3. Bot joins → same Recall webhook flow → insights
```

### 11.4 Workflow: Recording Control (Stop/Start)

```
Trigger: User clicks "Stop Recording" in Elevate UI
  ↓
1. POST /api/v1/recording-control {action: "stop", scope: "occurrence",
event_id}
  ↓
2. Handler:
   → Feature flag check
   → Load calendar event
   → Resolve scope (single/occurrence/series)
   → Enforce cutoff threshold
   → Detect platform (MS vs Recall)
  ↓
3a. MS Platform:
    → Write STATE_DISABLED override
    → Mark override target as "due"
    → Queue reconcile sweep
    → Sweep: PATCH meeting to disable transcription
  ↓
3b. Recall Platform:
    → Write override
    → Queue bot cancel task → DELETE bot at Recall API
    → For series: fan out cancel across all occurrences
  ↓
4. Start is the reverse:
   MS: Write STATE_ENABLED → sweep re-enables transcription
   Recall: Delete override → re-create bot
```

### 11.5 Workflow: Jira Ticket Sentiment Analysis

```
Trigger: Jira sends webhook for ticket create/update/comment
  ↓
1. POST /api/v1/jira/webhooks/jsm-ticket-events {webhookEvent, issue:
{key}}
  ↓
2. Handler debounces (10s Redis coalesce per issue_key)
  ↓
3. process_jsm_ticket_realtime_sync
   → Fetch ticket + comments from Jira API
   → Upsert ticket in jsm_tickets table
   → Upsert comments in jsm_ticket_comments table
   → Queue process_jsm_ticket_sentiment_analysis
  ↓
4. process_jsm_ticket_sentiment_analysis
   → Load ticket + comments
   → Render jsm_ticket_sentiment prompt template
   → LLM call → parse sentiment scores
   → Store in jsm_ticket_sentiments table
```

### 11.6 Workflow: Transcript Purge

```
Trigger: DELETE /api/v1/transcripts/{id}
  ↓
1. Resolve project_id and customer_id (before deletion)
2. Delete S3 object (if completed s3_storage row exists)
3. Delete alerts for this transcript
4. Delete s3_storage row
5. Delete transcript row (CASCADE deletes 7 child tables:
   insights, action_items, commitments, sentiments,
   upsell_opportunities, attendance, stage_insights)
6. mark_dirty() → triggers AI insight refresh for project/customer
```

## 12. Application and Runtime Lifecycle

### 12.1 Application Startup Sequence

```
1. Docker entrypoint: docker/entrypoint.sh
   → Run: alembic upgrade head (apply all pending migrations)
   → If OTEL configured: wrap with opentelemetry-instrument
   → Start: uvicorn src.main:app --host 0.0.0.0 --port 8000
     (--reload in dev mode)

2. Uvicorn loads src/main.py:
   → FastAPI() created
   → CORS middleware added
   → Logging middleware added
   → 26 routers registered under /api/v1
   → Health check endpoints registered
   → src/core/config.py: Config loaded from env on first access
(lru_cache)
   → src/db_engine/db.py: SQLAlchemy engine created on first import
   → src/core/redis.py: Redis pool created on first access (lru_cache)
   → App is ready to serve HTTP requests

3. Celery Worker (separate container, same image):
   → celery -A src.worker.app:celery_app worker ...
   → src/worker/app.py: celery_app configured
   → Task modules loaded from include list
   → Queues registered from routing.py
   → Signals connected (task_prerun, task_postrun, task_failure)
   → Worker ready to consume tasks from Redis

4. Celery Beat (separate container, same image):
   → celery -A src.worker.app:celery_app beat ...
   → Beat schedule loaded from app config
   → Starts firing periodic tasks
```

### 12.2 Request Processing Lifecycle

```
1. HTTP request arrives at Uvicorn
2. ASGI → FastAPI
3. LoggingMiddleware.dispatch():
   - Extract/generate trace_id, request_id
   - Set context vars
   - Log "Request started"
4. CORSMiddleware: validate origin
5. FastAPI routing: match path → router → handler function
6. Pydantic validation: parse request body/params against schema
7. Handler executes:
   - Load data via repositories (db_session)
   - Apply business rules
   - Enqueue Celery tasks (send_task_with_trace)
8. Response serialized via Pydantic schema
9. LoggingMiddleware: log "Request completed", add trace headers
10. HTTP response returned
```

### 12.3 Shutdown

**NOT FOUND:** No explicit shutdown/cleanup hooks. Uvicorn handles
graceful shutdown. Celery workers use `task_acks_late=True` to requeue
in-progress tasks on crash.
