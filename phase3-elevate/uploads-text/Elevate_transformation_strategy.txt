1. Executive summary (for CEO / CTO)

Elevate AI is a FastAPI + Celery backend that captures Microsoft Teams meetings (via Microsoft
Graph webhooks) and externally-hosted meetings (via Recall AI bots), transcribes them, and runs
each transcript through an LLM (via LiteLLM) to produce seven insight types — summary,
minutes, key notes, action items, commitments, sentiment, and upsell opportunities — plus
cross-entity insights (customer sentiment trends, project alerts). It also syncs Jira/JSM, Tempo
worklogs, and runs JSM-ticket sentiment analysis. It exposes 26 REST routers under /api/v1,
consumed by a separate Elevate web frontend (not in this repo). (VERIFIED stack; AUDIT
workflow breadth.)



The engineering is genuinely competent for its stage: a strict layered architecture (routes
handlers repositories/services; worker tasks worker utils), one dedicated Celery queue per
task type (74 queues) so no slow task blocks another, acks_late + reject_on_worker_lost for
crash-safety, Redis deduplication on at-least-once webhooks, OpenTelemetry tracing to SigNoz, a
multi-stage non-root Dockerfile, and ~180 test files. This is not a prototype; it is a maintainable
service built by someone who knows the patterns. (VERIFIED.)



The three findings that matter most:


1. There is no authentication or authorization on the API. Zero auth dependencies exist on any of
   the 26 routers (VERIFIED). If nothing upstream enforces it, every endpoint — including ones
   that create recording bots, delete transcripts, and trigger LLM spend — is open. This is the
   single highest-priority item to confirm and, if unmitigated, close. It is almost certainly handled
   by an upstream proxy/gateway today (the users/roles/role_permissions tables exist), but that
   must be confirmed, not assumed.
2. The product's defensible idea is real, but its moat is not the feature list. Elevate's distinctive
   combination — sentiment across both meetings and JSM tickets on one bounded −100/+100
   scale, framed as delivery/project health (not CS-ops), with a first-party notetaker and an
   interactive Teams bot — is not matched as a whole by any single competitor reviewed
   (RESEARCH). But each element individually is one roadmap step away for Planhat, Avoma,
   Fireflies, or Rocketlane. The moat has to be built deliberately: evidence-grounded, explainable
   insights tied to Kensium's own delivery data, not more insight types.
3. "Beyond Planhat" is not a stack question. The current stack can carry Elevate to a credible
   commercial product. What stands between "works internally" and "sellable" is not FastAPI vs.
   anything else — it is enterprise readiness (SSO, SCIM, SOC 2, tenant isolation, data-residency,
   recording-consent) and evidence that a buyer exists. None of that is in the repo today, and
   none of it is a framework choice.


The ten highest-priority decisions are collected in Section 14. The single most important:
confirm how auth is enforced in production before anything else.

3. What Elevate is and the problem it solves

The problem. Kensium runs many parallel commerce/ERP implementation projects. Delivery
health — is this customer slipping, is this project at risk, did we commit to something we're not
delivering — lives scattered across Teams calls, Jira/JSM tickets, and worklogs, where no human
reliably reads all of it. Elevate's thesis: observe those surfaces automatically, score sentiment
and risk, and surface it to delivery/CS/sales/leadership in one place "without toggling between
tools." (Vendor user guide; RESEARCH.)



What it does today (AUDIT, structurally VERIFIED):


   Captures Teams meetings via MS Graph transcript-subscription webhooks; captures external
   meetings (Zoom/Meet) via Recall AI bots.
   Stores transcripts (VTT) in PostgreSQL and recordings in S3 (SharePoint S3migration path
   exists).
   Runs 7 per-meeting LLM insight types + per-JSM-ticket sentiment + 2 cross-entity aggregates
   (customer sentiment trend, project alerts).
   Syncs Jira accounts/customers/projects/licenses + Tempo worklogs on schedules; JSM
   tickets in real time via webhook.
   Lets users stop/start recording per occurrence or series, trigger on-demand recording, and
   enforce Do-Not-Record domain policies.
   Emits an email on meeting-insight completion; sends pre-meeting chat notices in Teams.


What makes it not a generic meeting summarizer (INFERRED from architecture): the cross-entity
layer. Per-meeting summaries are commodity. Elevate's mark_dirty
process_ai_insight_customer_sentiment_trend / project_alerts pipeline aggregates across
meetings and tickets per customer/project — that aggregation, tied to Kensium's delivery context,
is the part a horizontal notetaker does not do.

4. Current architecture and component
responsibilities (VERIFIED structure)

Strict one-directional layering, no circular imports (AUDIT; consistent with code):


1. Routes (src/routes/, 26 routers) — thin controllers; validate via Pydantic, call handlers.
2. Handlers (src/handlers/) — business orchestration; decide what to do, enqueue Celery work.
3. Repositories (src/repositories/) — DB CRUD; own commit/rollback.
4. Services (src/services/) — external API clients (MS Graph 35+ files, Jira, Recall AI, Tempo,
   AWS S3, LiteLLM); no DB access.
5. Worker tasks (src/worker/tasks/) — thin .delay() wrappers.
6. Worker utils (src/worker/utils/) — the real background business logic.
7. Models (src/models/, 38+ SQLModel classes) / Schemas (src/schemas/, Pydantic).


Cross-cutting (VERIFIED): core/config.py (Pydantic BaseSettings, all env vars + feature flags,
@lru_cache singleton); core/redis.py (pooled client, max 50 conns, singleton); db_engine/db.py
(get_session FastAPI dependency + db_session Celery context manager; pool size 5,
max_overflow 10, recycle 1800s); middleware/logging.py (trace_id/request_id injection); worker/
signals.py (trace propagation into tasks); worker/routing.py (queue-per-task).



Runtime topology (VERIFIED from docker-compose + Dockerfile): 5 compose services — app
(Uvicorn:8000), celery-worker, celery-beat, redis:7.4, otel-agent. PostgreSQL is external/managed
(commented out of compose). Multi-stage Dockerfile, non-root kensium user, dev/prod stages.
Entrypoint runs alembic upgrade head then starts Uvicorn.

Background lifecycle (VERIFIED): Celery Beat fires 14 scheduled jobs (daily syncs, 15/20-min

6. [MEDIUM] LLM output parsing can fail silently (AUDIT/INFERRED). No structured-output

10. Current AI implementation and its limits
(VERIFIED)

What it is: direct LLM completion calls through LiteLLM. run(messages, insight_type,
reference_id) creates an llm_runs row (status pending), calls completion() (temperature omitted
for gpt-5/o1/o3/o4 families — VERIFIED), parses the response, updates the run (completed/
failed, tokens, model). Prompts are Jinja2 system.md.jinja + user.md.jinja pairs per insight type
(11 template sets).



What it is NOT (VERIFIED — these are genuinely absent, not just undocumented):


   No RAG, no embeddings, no vector search — confirmed by grep; the only "embedding" strings
   are SQL-escape docstrings.
   No tool-calling, no agents, no orchestration framework — direct completion only.
   No structured-output schema enforcement at the LLM boundary (INFERRED from repository
   store operations; no Pydantic-validated function-calling visible).
   No evaluation suite / regression tests for AI quality — 180 tests, but AI quality is not among
   them (AUDIT; 1 temperature test).
   No retry at the LLM layer — relies on Celery retry (AUDIT).


This is the right starting point, not a deficiency. Direct completion with a provider abstraction is
simpler, cheaper, and more debuggable than RAG/agents for fixed-shape insight generation. The
gaps that actually matter:


1. Structured outputs + schema validation (S effort, high value). Validate every parsed insight
   against a Pydantic schema; reject/repair on failure. Kills the silent-parse-failure risk.
2. An evaluation harness (M effort, high value). Labelled set of meetings/tickets measure
   action-item precision/recall, sentiment agreement, hallucination/citation correctness, cost &
   latency per meeting. Without it, no one can tell whether a prompt or model change helped.
   This is the prerequisite for any AI improvement.
3. Evidence-grounded insights with citations (M effort, differentiator). Make each sentiment
   score / risk alert cite the specific transcript turns and ticket comments that drove it. Buyers
   now ask for AI explainability, and no competitor has made it their core positioning
   (RESEARCH). This is Elevate's most defensible AI wedge and it uses data the system already
   has — no RAG required, just span attribution.
4. Grounded natural-language Q&A ("why is this customer at risk?") — this is where RAG/
   semantic retrieval might be justified later, but start with structured SQL over the existing
   insight tables + citations; only add pgvector if keyword/SQL retrieval measurably misses.


Graduated AI-action path (do in order, never skip the gate): summarize recommend draft
(ticket/follow-up) execute approved action via integration limited autonomy only after reliable
permissions, evals, audit, and human oversight exist. Never let an AI inference become a
business fact or trigger an irreversible action automatically.
