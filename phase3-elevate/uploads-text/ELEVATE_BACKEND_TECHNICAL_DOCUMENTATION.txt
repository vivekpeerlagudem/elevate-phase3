                     1. Executive Overview
                     Elevate 2.0 API is an ASP.NET Core 8.0 Web API that serves as the backend data
                     layer for the Kensium Elevate platform. It provides RESTful endpoints for
                     managing customers, projects, users, meetings, meeting insights, and a role-
                     based access control (RBAC) system.

                     The API connects to two separate PostgreSQL databases:

                        elevate — stores customers, projects, users, roles, modules, role permissions,
                        and role assignments
                        Meetings — stores Microsoft Teams meeting records and AI-generated
                        meeting insights

                     Key characteristics of this codebase:

                        Read-heavy: Most controllers are read-only; only Roles, RolePermissions, and
                        Users have write operations.
                        No authentication middleware: Despite login endpoints existing, no
                        JWT/OAuth tokens are generated or validated.
                        Jira-sourced data: Customers and Projects originate from Jira (evidenced by
                         IssueId / IssueKey fields).
                        Microsoft integration: Users reference Microsoft Entra IDs ( MsUserId );
                        meetings come from MS Teams.
                        AI-powered insights: Meeting insights are generated by an LLM pipeline
                        (table prefix ai_pm_llm_ ).

                       This documentation is based entirely on static code analysis. No runtime testing,
                       database inspection, or backend execution was performed. Claims about behavior
                       are derived from source code only.

                     4. Application Initialization and Entry
                     Point

                     The application uses .NET 8's minimal hosting model with a single Program.cs
                     file (no Startup class).


                     Startup Sequence (Program.cs)

                      1. Service Registration
                            Adds MVC controllers with JsonStringEnumConverter for enum
                            serialization
                            Adds Swagger/OpenAPI endpoints explorer and generator
                            Adds health checks (basic, no database probe)
                      2. Database Configuration
                            Reads DefaultConnection connection string for the elevate database
                            Creates an NpgsqlDataSource with PermissionType enum mapping
                            Registers ApplicationDbContext with this data source
                            Reads MeetingsConnection for the Meetings database
                            Creates a second NpgsqlDataSource and registers MeetingsDbContext
                      3. CORS Configuration
                            Adds an "AllowAll" CORS policy: any origin, any method, any header
                      4. Middleware Pipeline
                            Swagger UI enabled in all environments (including production) at
                             /swagger
                            HTTPS redirection
                            CORS middleware
                             UseAuthorization() — registered but has no effect (no authentication
                            scheme configured)
                            Maps controller routes
                            Maps health check at /health

                       Hardcoded fallback credentials: Program.cs contains inline fallback connection
                       strings with database credentials. If the configuration file is missing or the key is
                       absent, these hardcoded values are used. Connection strings should be managed via
                       environment variables or secure vaults in production.

                     10. End-to-End Feature Workflows

                     10.1 User Login (Email-Only)

                     1. Client sends POST /api/User/login with body { "email":
                        "user@kensium.com" }
                     2. UserController.Login() validates the LoginRequest DTO (requires valid
                        email format)
                     3. Queries ApplicationDbContext.Users with case-insensitive email match:
                         u.Email.ToLower() == email.ToLower()
                     4. If user not found → returns 401 { message: "Invalid email address" }
                     5. If user.IsRemoved == true → returns 403 { message: "Your account has
                        been deactivated..." }
                     6. Returns 200 with the full User entity object
                     7. No token is generated. The client receives the user object and is expected to
                        manage session state independently.


                     10.2 User Login (With Password)

                     1. Client sends POST /api/User/login-with-password with { "email":
                        "...", "passwordHash": "..." }
                     2. UserController.LoginWithPassword() validates the
                         LoginWithPasswordRequest DTO
                     3. Queries users by email (case-insensitive)
                     4. Compares user.PasswordHash == dto.PasswordHash (direct string
                        comparison)
                     5. If mismatch → 401 { message: "Invalid password" }
                     6. If removed → 403
                     7. Returns 200 with the full User entity


                     10.3 Viewing Active Customers

                     1. Client sends GET /api/Customer/active
                     2. CustomerController.GetActiveCustomers() queries customers with:
                             Status == "Active Customers" || Status == "Internal Customer"

                     8. Admin views effective permissions: GET

                     4. Insights are generated by an external AI pipeline — this API only reads the

                     How roles map to users

                     RoleAssignment does not directly reference a User ID. Instead, it maps a Role to
                     a department + job_title combination. A frontend or consuming application
                     would match users to roles by comparing the user's Department and JobTitle
                     fields against role assignments.
